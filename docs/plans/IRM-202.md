# IRM-202: Bank transaction list silently stops at 1000 rows

`listTransactions` in `src/server/bank.server.ts` returns the newest 1000 rows of an account (`.limit(1000)`) and says nothing when more exist. A file import can add up to 10 MB of lines, so a busy account passes 1000 rows after one or two imports.

## Acceptance criteria

* The list can reach every transaction of an account: paging by a cursor or an explicit "more" flag.
* The response tells the caller when there is a next page; it never truncates silently.
* A Vitest test against the real database imports more rows than the page size and reads them all back, in order, with no row twice.
* The UI that lists transactions (if any exists yet) loads the next page.

## Progress

- Branch created; no UI lists transactions yet (grep of `src/`), so the UI criterion is vacuous.
- Red then green: `npx vitest run src/server/bank.server.test.ts` (11 failed before, 14 passed after).

## Decisions

- Response is `{ items, next }`; `next` is an opaque keyset cursor `booking_date|created_at|id` or null. Client sends it back as `?cursor=`. Page size fixed at 1000.
- created_at is compared as text-cast timestamptz to keep microseconds; id breaks ties inside one import (same created_at).
- Wider class of bug: any other `.limit(n)` list that returns a bare array (`invoices.read.server.ts:88`, 500) can truncate silently the same way.
