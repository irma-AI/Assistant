# IRM-139: MCP server foundation with read-only tools, behind the existing session

See the Linear issue (description plus Decisions, shaped 2026-10-25).

## Progress
- `POST /api/v1/mcp` (`src/routes/api/v1/mcp.ts`, `src/server/mcp.server.ts`): Streamable HTTP with JSON replies, hand-written `initialize`, `ping`, `tools/list` and `tools/call` (no SDK dependency).
- Auth is the existing session (cookie or bearer); no session gives 401.
- Tools over the same server code as the API: `list_organisations`, `get_my_access`, `list_roles`, `list_members`. Each states its permission (`session` or `member`); the server code enforces membership.
- One audit row (`mcp_tool_called`: tool and User-Agent as client) per call; a refusal adds `authorization_refused`.
- Proof: `pnpm exec vitest run src/server/mcp` (session required for every tool, outsider refused, audit rows, demo session reads, bad arguments).

## Decisions
- No migration: `audit_events.event` is free text.
- Client name is the User-Agent, since the server is stateless and `initialize` clientInfo is not carried to later calls. IRM-178 can replace it with the OAuth client.
- Every tool is read-only, so demo sessions may call all of them; write tools (IRM-179) must call `refuseDemo`.
- Not done here: GET/SSE streaming, sessions, rate limits per token (IRM-178).
